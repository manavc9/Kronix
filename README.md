# Kronix — Railcar Repair Operations Platform

A full-stack web application for managing railcar repair shop operations across multiple facilities. Built to solve the real scheduling chaos in reactive repair environments — where customer approvals, found work during repairs, and unpredictable material lead times make traditional scheduling methods fail.

## The Problem

In railcar repair, roughly 4 out of 10 cars hit disruptions mid-process: unexpected damage found during inspection, customer approval delays (2–15+ days), or material backlogs. Each disruption cascades across every other car's projected completion date, sometimes reshuffling the entire shop schedule two months out. Standard manufacturing scheduling doesn't work here — this is a reactive, pull-type environment where the schedule is an output of flow discipline, not an input.

## What Kronix Does

- **Multi-facility management**: Track cars, spots, and work orders across multiple shop locations from a single dashboard
- **Visual scheduling**: Gantt-style bay board showing spot assignments, car positions, and timeline conflicts at a glance
- **Full car lifecycle tracking**: From inbound arrival through inspection, quoting, customer approval, work order creation, cleaning, repair, outbound inspection, and final disposition
- **Role-based workflow**: Schedulers, CSRs, Shop Managers, and Admins each see what's relevant to their role
- **Yard and cleaning management**: Track yard positions and cleaning rack flow separately from main repair bays
- **Work order management**: Revenue tracking, hours estimation, parts status, and material blocker visibility per car
- **Reporting**: Export monthly summaries, WIP status, shop utilization, yard status, and parts delay reports as Excel or PDF

## Tech Stack

- **Backend**: Python / Flask
- **Database**: SQLite (development) — designed for easy migration to PostgreSQL for production
- **Frontend**: Jinja2 templates, HTML/CSS/JS
- **Server**: Gunicorn (production), Flask dev server (local)

## Quick Start

```bash
# 1. Clone the repo
git clone <repo-url>
cd kronix

# 2. Create and activate a virtual environment
python -m venv venv
venv\Scripts\activate      # Windows
# source venv/bin/activate  # Mac / Linux

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure environment
cp .env.example .env
# Edit .env and set SECRET_KEY to a random string

# 5. Run locally
python run.py
```

Open [http://127.0.0.1:5000](http://127.0.0.1:5000) — a login screen will appear with all available users.

### Loading demo data (~220+ cars across 3 facilities)

```bash
python seed_demo_data.py
```

This seeds realistic work orders at various pipeline stages across Thornfield, Harwick, and Delverton shops. Run it after the app has started at least once (so the database and base records exist).

## Deploying to Render

The repo includes a `render.yaml` blueprint. Click **New > Blueprint** in the Render dashboard, connect this repo, and Render will provision the service automatically. `SECRET_KEY` is auto-generated by Render on first deploy.

## What's Next

The next phase adds a **"what-if" scheduling engine** — click any car and see exactly how calling it in next would cascade across every other car's projected completion date, with the app recommending the optimal call-in sequence based on spot availability, labour hours, and material readiness. Built on a deterministic constraint solver (not AI/LLM), so the math is exact and runs fully offline.
